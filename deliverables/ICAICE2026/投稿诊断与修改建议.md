
跑出来的**真实**结果（450 次规则执行 + 200 组网格 + 150 条金标输出审计）：

| 实验 | 关键数字 |
|---|---|
| 覆盖回放 | 450 次执行；PERSONAL_GAP 17.3%、EXAM_RESULT 8.0%、REPORT_ANALYSIS 84.7% 命中；88.0% 档案至少命中一条 |
| **缺陷 1** | 考试规则阈值写死 60，业务合格线是 80/85 → **80.0% 静默漏报**，精确率却 100% |
| **缺陷 2** | 技能规则写死 `required_level = 3` → **62.7% 真实等级差距漏报**；未来需求轴 120 条无任何规则覆盖 |
| **缺陷 3** | `REPORT_GAS_WITHIN_NEAR` 只写了 `ratio ≤ 0.10` 没写下界 → 终端规则 `REPORT_GAS_WITHIN` **在 200 组网格里一次都没命中**（不可达），40 组舒适读数 100% 被误升档成「中」 |
| 确定性 | 450 次执行逐字节一致 100%；打乱规则物理顺序后结论仍 100% 一致 |
| 延迟 | 进程内规则求值 p50 0.0074 ms / p95 0.0128 ms（已注明不含 DB/模型/网络） |
| 护栏审计 | 金标输出契约/算术/映射/优先级/截止日/安全边界/依据可回指 **全部 100%**；数字可溯源 99.8%（2324 个数字里 4 个无出处） |

## 七、更好建议（超出"改稿"的部分）

**1. 你的学术贡献其实不是"做了个 Agent"，而是那套工程契约。**
原稿把它写成了"我们提了个框架"。真正站得住、且别人没有的是：
- 规则存 MySQL JSON 列、算子白名单、**分组级** `stop_on_match` / `max_hits`（不是场景级）；
- `*_from` 引用事实让 1 条规则服务 5 种气体 × 6 个档位（不写 30 条）；
- `source ∈ {rule, model}` 契约隔离，换模型不动 Controller/DTO/前端；
- 一个 `run_id` 串起 `rule_result → agent_suggestion → decision_log`，Agent 只建议、绝不改业务数据。
这四点我在论文里都写成了编号贡献，并且每一条都对应你代码里真实存在的东西——审稿人问到哪条你都答得上来。

**2. 把"审计自己规则集的缺陷"当成卖点，不要藏着。**
大多数 EI 论文只报喜。你这篇里 80% 漏报、不可达规则、安全盲区，恰恰是最有说服力的部分——它证明了"规则增强"这个方向必须配一个审计 harness，否则规则集会悄悄腐烂。这是全文最有新意的贡献，我把它放到了摘要和结论里。

**3. 审稿人最可能问的 4 个问题（提前准备）**
- 「为什么不用 Drools？」→ 硬约束只允许 MySQL + 无 ORM；且数据库规则让管理员改库即生效，不需要发布。
- 「150 条样本是不是太少？」→ 评测对象是**规则集**不是模型；150 条是真实档案全量，且每条执行两次做确定性验证。
- 「没有和 M1–M4 对比？」→ 如实回答：模型路径尚未接入，本文的评测对象是规则层与护栏层，模型对比列为 future work（论文第 VII 节已这么写）。
- 「图 1/图 2 的依据？」→ 全部来自 `docs/rule-engine-design.md` 与 `docs/api-catalog.md`，可现场打开代码对照。

**4. 投稿节奏建议（今天 10-16）**
