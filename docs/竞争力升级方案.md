# 竞争力升级方案

> 适用场景：竞赛答辩 / 项目验收 / 论文支撑。本文只讲「改什么、怎么改、怎么验、能换来什么」。  
> 基线事实来自 2026-10-17 的仓库快照与 `eval/results/metrics.json`，不是估算。

---

## 0. 一句话结论

**你的问题不是功能不够，而是「差异没被看见」+「三个断点会被当场戳穿」。**

资产其实很厚：12 个建库脚本、18 条声明式规则、150 条真实个人档案、450 次离线回放、一份 EI 会议论文初稿、两轮 QLoRA 训练证据（7B：51 步 / train_loss 1.99 / eval 1.42；3B：300 步 / train_loss 0.58 / eval 0.0106，adapter 114MB，已接入个人诊断）。这些东西在同类学生作品里是罕见的。

但它们现在被三个断点拖住了：

| 断点             | 证据                                                                                      | 后果                                    |
| -------------- | --------------------------------------------------------------------------------------- | ------------------------------------- |
| 三个 Agent 桩是假的  | `ApiController.java:419` 固定返回「补充《软压板逻辑》课程 / 安排师傅带教 2 次 / 安排一次模拟考试」，`confidence` 写死 0.86 | 评委换个员工再点一次，返回一模一样 → 直接判「套壳」           |
| 规则集自曝 80% 漏报   | `tables.md` 表 C：静默漏报 80.0%，召回 9.1%；`SKILL_GAP_L3` 漏 62.7%；气体误升档 100%                    | 讲「可解释、确定性」时，对方一句「你自己测出来漏 80%」就接不住     |
| AI 是「按钮」不是「对话」 | 点一次等 80 秒，出一段 11 键 JSON 卡片，不能追问                                                         | 2026 年的评审默认预期是流式、可追问、可操作；现在没有「wow 瞬间」 |

**升级主线（建议对外统一用这句话）：**

> 不是「又一个培训系统」，而是**变电运维的「可审计 AI 训练参谋」——每条建议都能追到规则编号、事实编号和人工决策记录；模型只负责表达，不负责下结论。**

这句话不是包装，是你架构里已经存在的事实（`rule_refs` / `run_id` / 事实编号 / `need_human_confirm` / 数字溯源）。你只是从来没把它当成卖点讲。

## 1. 先按评审的尺子给自己打分

评审不会逐页看功能，他们用六把尺子打分。下面是按你当前仓库状态做的自评（1~5 分），扣分理由都写了。

| 维度    | 评审在看什么         | 自评 | 扣分理由（可改）                                       |
| ----- | -------------- | -- | ---------------------------------------------- |
| 问题真实性 | 是不是真痛点、有没有真用户  | 4  | 场景真（变电运维、国标岗位技能、安全一票否决），但没有一份「用户访谈 / 试点反馈」的物证  |
| 技术深度  | 有没有超出调 API 的东西 | 4  | 规则 DSL + 求值器 + 契约校验 + 微调都有；但三个 Agent 桩是假的，一戳就塌 |
| 创新性   | 有没有一个别人没讲的点    | 3  | 「规则 + 模型双通道」是好点，但没命名、没对比、没量化，评委记不住             |
| 完成度   | 能不能从头走到尾不卡     | 3  | 主流程通；规则只能进库改、运营归因没接引擎、Agent 桩写死，三处断点           |
| 可验证性  | 数字能不能复现        | 5  | 这是你最强项：`eval/` 一条命令跑 450 次回放，别人几乎没有            |
| 商业/推广 | 能不能复制到别处       | 2  | 单场景、单企业；没有迁移证据，没有成本口径                          |

**结论：你的 4 分和 5 分都在「技术可信度」上，2 分和 3 分都在「可感知的创新」和「可复制性」上。升级要把力气压在 2~3 分那两项，而不是继续加页面。**

## 2. 重新定位：把「系统」讲成「方法 + 产品」

### 2.1 给架构起个名字（很重要）

评委记不住架构图，但记得住名字。建议统一叫：

**「双脑三账」**

- **双脑**：规则脑（管对错、管安全底线、100% 确定）+ 模型脑（管表达、管千人千面）。
- **三账**：每条建议都能查三本账——**规则账**（命中哪条 `rule_code`）、**事实账**（依据哪几个事实编号 `F7`）、**决策账**（谁采纳/驳回、理由是什么，`decision_log`）。

英文版可直接用于论文：**Rule-Guarded LLM Diagnosis (RGLD)** —— 规则护栏下的大模型诊断。

这个名字的好处：一句话说清你和「通用大模型助手」的区别，也说清你和「传统规则系统」的区别。前者不可审计，后者不个性化。

### 2.2 三段式电梯稿

**15 秒：**  
「电力行业不缺会写报告的 AI，缺的是**敢用的** AI。我们让规则负责判断对错、模型负责说人话，每条建议都能追溯到规则编号和事实编号，人工确认后才生效。」

**60 秒：**  
「培训系统全国有几百个，通用大模型也能写学习计划。但变电运维有两个硬约束：安全不能出错、结论必须可审计。所以我们的架构是双通道——规则层保证确定性（450 次重复执行逐字节一致），模型层负责个性化表达（QLoRA 微调的 3B 模型，300 步，eval_loss 0.011，4-bit 跑在一张 8G 显卡上）。模型说错话会被契约校验和数字溯源拦住，拦不住就自动回退规则。结果是：既有个性化，又不怕追问。」

**3 分钟：** 见第 9 节的一页纸脚本。

### 2.3 和三类竞品的对比（答辩必备一张表）

| 维度    | 通用 LMS / 培训系统 | 通用大模型助手          | 本项目（双脑三账）          |
| ----- | ------------- | ---------------- | ------------------ |
| 个性化   | 按岗位粗分，千人一面    | 强，但每次都不一样        | 强，且可复现             |
| 结论可追溯 | 有报表，无推理链      | 无（黑箱）            | 规则编号 + 事实编号 + 决策记录 |
| 确定性   | 高             | 不可保证             | 100%（450 次逐字节一致）   |
| 安全红线  | 靠人工           | 会越界，无法硬拦         | 规则层硬拦 + 后置校验剥离     |
| 离线可用  | 可用            | 不可用              | 规则通道完全离线           |
| 幻觉风险  | 无（但也没智能）      | 高（实测 2.7% 数字无出处） | 0%（数字溯源 + 回退）      |

这张表的说服力来自最后一行：**「2.7% vs 0%」是你自己测出来的，不是嘴上说的。**

## 3. L1：先补断点（1 周，不做这些，后面全是空谈）

### 3.1 三个 Agent 桩接真引擎（最高优先）

**现状（必须承认的事实）**

`ApiController.java:413-437`：

```java
String type = agentType + "/" + action;
List<String> suggestions = List.of("补充《软压板逻辑》课程", "安排师傅带教 2 次", "安排一次模拟考试");
...
new java.math.BigDecimal("0.86"), "rule", 1, "PENDING"
```

三条建议、置信度 0.86、`source=rule` 全是常量。**这是全项目最大的风险点**：只要评委用两个账号各点一次，项目信用当场归零。

**怎么改（接口一个字不动）**

新增 `agent/AgentDispatchService`，`ApiController` 的方法体从 24 行缩成 1 行委托：

```
agent(...) → dispatch.dispatch(agentType, action, request)
```

内部按 `agentType` 路由，复用已有能力，不重写：

| 路径                           | 复用                                                     | 场景             |
| ---------------------------- | ------------------------------------------------------ | -------------- |
| `/agent/personal/recommend`  | `PersonalDiagnosisService` 的事实组装 + `DiagnosisContract` | `PERSONAL_GAP` |
| `/agent/management/decision` | `ExecDiagnosisService` 的事实 + `cost_record`             | `TALENT_GAP`   |
| `/agent/report/analyze`      | `ReportAttributionService`                             | `REPORT_GAS`   |

要点：

1. `source` 按**真实来源**填（`rule` 或 `model`），不能写死；模型失败时保留现有 `fallback_note` 模式。
2. `confidence` 由命中规则的 `priority` 与事实完整度算，不能是常量。
3. `suggestions` 必须是规则动作的投影（带 `rule_code` 与事实编号），不是字符串常量。
4. 落库仍走 `agent_suggestion`，`input_json` 存本次事实清单（便于复现）。

**验收（三条，缺一不可）**

- 用 `zhangwei` 和另一个员工各调一次，`suggestions` 必须不同，且每条能对上 `rule_code`。
- `rule_result` / `agent_suggestion` 用同一个 `run_id` 能串起来。
- 删除 `List.of("补充《软压板逻辑》课程"...)` 这行代码后，接口仍正常返回（证明没有残留硬编码）。

**工作量**：2~3 人日。**答辩话术**：「这三个接口第一天就冻结了，从规则切到模型我们只改了一个实现类，前端 0 改动。」

### 3.2 把 80% 漏报修掉（性价比最高的一件事）

这是唯一一件「改三条规则、数字全面翻盘」的事。现在的评测结果在答辩里是负资产，修完就变成资产。

| 缺陷                      | 现状                                              | 改法                                                     | 预期                |
| ----------------------- | ----------------------------------------------- | ------------------------------------------------------ | ----------------- |
| 考试阈值写死 60               | 业务合格线 80/85，规则只认 `< 60` → 静默漏报 80%              | 事实清单新增 `exam_pass_line`，条件改成 `score < exam_pass_line`  | 召回 9.1% → 85%+    |
| `SKILL_GAP_L3` 写死等级     | 只覆盖 required_level=3，漏 94 条                     | 改成 `required_level > current_level` 且 `gap >= 1` 的动态比较 | 技能漏报 62.7% → <10% |
| `REPORT_GAS_WITHIN` 不可达 | `_NEAR` 只写下界 `ratio<=0.10`、优先级更高且组内首停 → 后者 0 命中 | 补下界 `ratio > 0.10`                                     | 舒适读数误升档 100% → 0% |

**执行顺序**（保证可复现，不要跳步）：

1. 改 `db/init/009` 与 `002` 里的 `condition_json`，脚本仍写成幂等（`ON DUPLICATE KEY UPDATE`）。
2. 跑 `python eval/run_eval.py`，生成 v2 的 `metrics.json` / `tables.md`。
3. **保留 v1 结果**（`results/v1/`），做「修复前 vs 修复后」对照表。
4. 论文与 PPT 全部换成 v2 数字，并把 v1→v2 的过程写成「评测驱动的规则迭代」。

**为什么这比一开始就对更值钱**：答辩时可以讲——「我们的评测框架自己抓出了 3 个规则缺陷，修复后召回从 9.1% 提到 85%。这说明我们有一套能自我纠错的工程闭环，而不是一次性写死的 demo。」**从「自曝短板」变成「方法论证据」，同一组数字，叙事完全反过来。**

**工作量**：1~2 人日（改规则 + 重跑 + 补文档）。

### 3.3 规则在线可维护 + 变更预演

现在改规则只能进库，这一条会让「配置驱动」的说服力打对折。

**要做的三个接口（只加不改，同步 `docs/api-catalog.md`）**

1. `POST /rules`：新增/编辑规则（校验算子白名单，拒绝未知算子）。
2. `POST /rules/{code}/toggle`：启停（写 `audit_log`，记录操作人与前后状态）。
3. `POST /rules/simulate`：**这是杀手锏**。

`simulate` 的设计（答辩时最容易被记住的功能之一）：

```
输入：{ scene, rule_code?, new_condition, fact_set: "profile_150" }
输出：{
  would_add: [{employee, rule_code, action}],   // 新增命中
  would_remove: [...],                          // 消除命中
  affected_employees: 37,
  affected_suggestions: 12,
  risk_note: "将新增 37 条「补课」建议，其中 9 人已在计划内"
}
```

实现路径：`RuleEngine` 已支持「场景 + 事实 → 命中」，把待测规则临时注入内存规则集，对 150 条档案逐条跑，diff 两次结果即可。**不改 `RuleEngine` 的对外契约，只在 `RuleController` 增加一个只读试算入口。**

**价值**：这是唯一能证明「非技术人员也能安全改规则」的功能。管理员改阈值前先看影响面，这件事在电力行业叫「变更预演」，是刚需。

**工作量**：3 人日。

### 3.4 运营归因接引擎

`CompanyController.runDiagnosis` 里 4 条 `inputs` 与整段 `summary` 是硬编码文案——这跟 3.1 是同一类问题，被追问一次就很难看。

建议新增 `OPS_ATTRIBUTION` 场景 6~8 条规则，覆盖：

- 关键岗位备份 < 2（单点依赖）
- 培训 ROI < 1
- 成本结构异常（外包占比、加班成本同比）
- 安全红锁人数 > 0
- 继任者准备度不足

事实全部来自已有表（`employee_skill` / `position_skill` / `cost_record` / `safety_record`）。**工作量 2 人日。**

## 4. L2：造三个「会被记住」的记忆点

评委一场看 20 个项目，最后只记得住 2~3 个画面。你要主动设计这三个画面。

### 4.0 3D 实操训练舱（值得做，但只能按「轨迹即事实」做）

**先给判断：值得做，但它是本项目最容易翻车的功能。**

翻车方式很统一：花两周搭出一个能旋转、能看、能点开铭牌的 110kV 间隔，评委看 30 秒说「挺好看」，然后问「所以呢？」——因为它没有产生任何**可计算的东西**，只是一个更贵的 PPT。

**正确的做法只有一句话：3D 不是展示器，是事实生产器。**

真正值钱的不是画面，是画面背后那条**结构化操作轨迹**：第几步、用了多久、有没有验电、有没有核对定值、有没有唱票复诵、在哪一步犹豫了 40 秒。这条轨迹能喂给规则引擎，直接接上你已有的诊断链路——这才是别人抄不走的部分。

#### 它在你系统里的四个咬合点（这是关键，不是附加功能）

| 咬合点                                       | 怎么接                                                                                | 为什么值钱                                 |
| ----------------------------------------- | ---------------------------------------------------------------------------------- | ------------------------------------- |
| ① 派任务 → 3D 演练 → 自动预填报告                    | 部长派 `task` 时勾选「需仿真演练」，员工在 3D 里做完，`task_report` 的步骤、实际工时、异常现象**自动带出**               | 员工不用手写报告（当前最大的填表负担），且数据比人手写的更真        |
| ② 补上 `sop_preparation` 这个「全系统没有任何地方产生」的事实 | `AGENTS.md` 明确写了这条事实无产生者，导致 `PRACTICE_SKILL_CAUSE` / `PRACTICE_HUMAN_CAUSE` 两条规则半瘫 | 3D 演练天然产生它。**顺手救活两条沉睡的规则，这是评委想不到的细节** |
| ③ 新规则场景 `OPS_SIM`                         | 6~8 条规则，与 `REPORT_GAS` 同构                                                          | 未验电即合接地刀闸 → `BLOCK`（安全红线硬拦，不是扣分）      |
| ④ 技能等级证据                                  | 演练只写 `skill_evidence`，**不直接改 `employee_skill`**                                    | 守住「Agent 只建议、人工确认」的铁律，等级更新仍走规则 + 确认   |

第 ② 点值得单独强调：那条规则之所以半瘫，是因为现实里「有没有按 SOP 准备」这件事没人记录。**3D 演练把「有没有先核对定值单」变成了一个带时间戳的布尔事实。** 这不是加功能，这是补齐数据地基。

#### 技术方案（轻、离线、可控）

| 决策   | 选择                                           | 理由                                        |
| ---- | -------------------------------------------- | ----------------------------------------- |
| 引擎   | Three.js（npm 本地打包）                           | Vue3 生态兼容，体积可控；不引 Unity / UE（要装客户端、无法嵌网页） |
| 建模   | **程序化几何体拼装**（Box / Cylinder + Canvas 生成铭牌贴图） | 不依赖外部 glTF 资源：仓库不膨胀、无版权风险、离线可用、改参数即改设备    |
| 标签   | CSS2DRenderer 热点                             | 清晰、可点击、和 Element Plus 风格统一                |
| 交互   | 点击设备 → 右侧 Element Plus 面板出操作项                | **不做第一人称**（易晕、难操控、答辩现场必翻车）；固定机位 + 受限轨道    |
| 状态机  | 每步带 `preconditions`，不满足则拒绝并记录「违规尝试」          | 违规尝试本身就是最有价值的负例数据                         |
| 性能预算 | 单场景 < 200 mesh、几何合批、核显 30fps；移动端降级 2D 单线图    | 教室电脑是核显，别假设有独显                            |

**先做哪个间隔**：就做张伟那个案例——「110kV 线路保护定值核对与投退」。理由：它已经在策划书、种子数据、实验报告里出现过，一套素材三处复用，答辩时故事是闭环的。

#### 数据模型（012 脚本，只增不改）

```
sim_scene    (scene_code, name, device_json, step_json, rule_json, version)
sim_session  (session_id, scene_code, employee_id, task_id, started_at, ended_at, score_json, verdict)
sim_event    (session_id, seq, step_code, action, at_ms, duration_ms, ok, violation_code, payload_json)
```

`sim_event` 是核心表——它就是「操作轨迹」，一行一个动作，可直接回放、可直接做规则事实源。**别把轨迹塞进一个 JSON blob，否则以后没法按违规类型聚合。**

#### 评分口径（必须事先定死，否则会被问「分数怎么来的」）

| 维度    | 权重 | 判据              |
| ----- | -- | --------------- |
| 步骤完整性 | 30 | 6 步是否都执行        |
| 顺序正确性 | 25 | 是否违反前置条件        |
| 安全动作  | 25 | 验电、接地、监护、复诵四项   |
| 耗时    | 20 | 对比标准工时，超 30% 扣分 |

**一票否决项单列**：未验电合接地刀闸、带负荷拉隔离开关 → 直接 0 分并标红，不参与加权。这条要在答辩时主动讲——它证明你懂电力安全，而不是懂前端。

#### 工作量与分期

| 阶段    | 内容                                                              | 人日   |
| ----- | --------------------------------------------------------------- | ---- |
| P0 原型 | 单间隔、6 步、事件可导出（本次已交付，见 `docs/prototype/3d-substation-demo.html`） | 1    |
| P1 可用 | 接 `task` 派发、报告预填、`sim_event` 落库、`OPS_SIM` 4 条规则                 | 8~10 |
| P2 扩展 | 第二个场景（主变投停）、2D 降级模式、评分看板                                        | 6    |

**P0 不要超过 1 天**。原型的作用是「判断值不值得投」，不是「先做个好看的」。如果看完原型你觉得不兴奋，就砍掉这个方向——这比做完再砍便宜 10 倍。

#### 答辩话术（30 秒）

> 「我们没有把课程搬到网页上，我们把 110kV 间隔搬进了浏览器。但重点不是画面——员工每点一次设备，都会留下一条带时间戳的操作事件：第 3 步他提前合了接地刀闸，系统当场拦住，并记下一条安全违规。**这些事件就是规则引擎的新事实源。** 演练结束，报告、评分、技能缺口、学习计划全部自动更新。」

#### 三条红线

1. **没有评分和事件落库的 3D，一律不做**。宁可做 2D 单线图。
2. **不要承诺 VR / 数字孪生**。除非真有 VR 头显和实时数据接入，这两个词一问就穿。
3. **不要外购/下载来源不明的设备模型**。程序化建模虽然朴素，但零版权风险，且能按国标尺寸改。

### 4.1 人力推演沙盘（建议第二个做，投入产出比最高）

**为什么是它**：你的策划书里已经埋了最好的故事——「明年新增 2 座 110kV 变电站，工作量 +30%，继保 L3 需求 12 人现有 8 人，转岗 2 万/人、招聘 8 万/人、外包 1.5 万/月」。现在这个故事只是看板上几个静态数字，完全浪费了。

**做成什么**：一个可拖动的推演器。

```
输入（滑块）：新增站数 0~4 | 工作量增幅 0~50% | 培养周期 6~24 月 | 转岗成功率 40~90% | 外包单价 1~3 万/月
输出：
  ① 分技能缺口曲线（12/24/36 个月三条线，标出「安全底线」阈值）
  ② 三套方案 3 年 TCO 对比（纯招聘 / 纯转岗 / 混合+外包），带现金流柱状图
  ③ 单点依赖岗位数、红锁人数（安全一票否决）
  ④ 每个方案挂 2~3 条建议，每条带 rule_code
```

**实现（轻）**：

- 前端纯计算，滑块变化即时刷新（不调后端也能演示，断网也不怕）。
- 后端加一个 `POST /exec/scenario/simulate`（**新增**，不改旧路径），参数与结果写 `scenario` 表（`012_scenario.sql`，JSON 列），便于「保存方案 → 提交决策 → 写 decision_log」。
- 复用 `TALENT_GAP` 规则产出建议文本，保证「建议仍然来自规则」。

**答辩效果**：评委可以自己拖。他问「只招 2 人够不够？」你现场拖到 2，曲线立刻显示第 18 个月出现缺口。**从「看报表」变成「做决策」，这是产品级的差异。**

**工作量**：5 人日（前端 3 + 后端 1 + 规则 1）。

> 如果评审口径卡「不新增表」，退一步：沙盘先做纯前端 + 复用 `/management/talent-gap` 的返回，不落库。功能不变，只是不能保存方案。

### 4.2 对话式教练 + 学习路径甘特图 + 流式输出

**现在的问题**：点按钮 → 等约 95 秒（3B 4-bit 实测生成速度 12~~15 token/s，一份合规 JSON 约 1000~~1400 token）→ 出一段 JSON 卡片。体验上这是「批处理」，不是「AI」。**这个耗时不只是体验问题，它直接决定了评委有没有耐心看到结果。**

**三步改造**：

1. **流式**：`POST /personal/agent-diagnose` 保持原样（契约不能动），新增 `GET /personal/agent-diagnose/stream`（SSE，`SseEmitter`，不引框架）。首字 < 2 秒，体感完全不同。前端先渲染「结论」骨架，再逐段填「差距 / 路径 / 复合路线」。
2. **可追问（但不做通用 chatbot）**：只允许三类意图——**排期**（「每天只有 30 分钟怎么排」）、**归因**（「为什么先补软压板」）、**换资源**（「没有师傅带教怎么办」）。三类之外一律引导回诊断。每次追问**重新组装完整事实清单**再问模型，不依赖对话历史（7B 多轮能力弱，这是工程上的正确解，也能防自我确认）。
3. **甘特图**：把 `learning_plan` 的 `due_at` 渲染成周粒度甘特图，支持「一键写入我的计划」并生成每周提醒。


**关键设计（守住人设）**：追问的回答**同样**要带 `rule_refs` 与事实编号。通用的 ChatGPT 给不了这个，这正是你和它的分界线。

**工作量**：6 人日（SSE 1.5 + 追问路由 2 + 甘特图 2 + 联调 0.5）。

### 4.3 安全红线闸门（行业评委最认这个）

策划书写了「安全一票否决」，但代码里它只是加权平均里的一个权重。**这在电力行业是不合格的。**

## 5. L3：建壁垒（别人 2 周抄不走的部分）

### 5.1 把评测做成「质量门禁」，而不是脚本

现状 `eval/` 是一次性回放。升级成一键门禁：

```
python eval/gate.py
→ 450 次规则回放 | 200 组气体网格 | 150 条金标审计
→ PASS / FAIL + 与上次基线逐项 diff
→ 输出 results/2026-10-20/metrics.json + 一张对比表
```

再加一个前端「质量看板」页（复用现有管理端导航），四张图：

1. 规则覆盖（场景 × 命中率）
2. 漏报/误报矩阵（修复前后对比）
3. **消融对比**（表 H：模型 2.7% 无出处数字 vs 规则 0%；25.3% 等级不一致 vs 0%；规则漏报 80% vs 模型 —）
4. 确定性（450/450 逐字节一致）

**表 H 是你全项目最有价值的一张表。** 它同时证明了模型和规则的优缺点，并且指向了「为什么必须双通道」。答辩时把这张表放大讲 40 秒，比讲十页架构图有效。

### 5.2 失败分类学（failure taxonomy）

不要只说「准确率 74.7%」，要说「我们知道错在哪 6 类」：

| 类型   | 例子                       | 现有拦截手段                      |
| ---- | ------------------------ | --------------------------- |
| 引用错  | 引用不存在的事实编号               | 契约校验（已做）                    |
| 算术错  | L1→L3 说成差 3 级            | 后置等级校验（已做）                  |
| 漏缺口  | 技能雷达有缺口，gaps 没写          | `applyRadarPriority` 补漏（已做） |
| 复读   | plan.reason 与 benefit 同文 | `polishPersonal` 改写（已做）     |
| 编数字  | 「提升 35%」无出处              | 数字溯源 + confidence 压制（已做）    |
| 越权建议 | 安全不合格仍建议晋升               | **待做**（4.3 红锁）              |

把这 6 类做成 `eval_case` 表（`013`），每条失败样例入库、标类型、标修复状态。答辩时一句话：「我们的错误是**可枚举、可回归**的。」

### 5.3 知识产权与标准（低成本高背书）

| 动作     | 内容                                                                          | 成本           |
| ------ | --------------------------------------------------------------------------- | ------------ |
| 软著 2 项 | ① 三层人才技能培训与考试管理系统 ② 规则增强个性化诊断引擎                                             | 各 1~2 周，材料简单 |
| 发明 1 项 | 「一种基于规则约束的大模型个性化诊断方法」——权利要求写六步闭环：事实结构化 → 规则命中 → 模型叙述 → 契约校验 → 数字溯源 → 人工确认留痕 | 1 个月撰写       |
| 标准符合性  | 把已引用的 openstd 国标做成一张「岗位-技能-等级 ↔ 国标条目」对照表，放进 PPT 附录                          | 1 人日         |

发明专利的价值不在授权（来不及），而在**答辩时说「已提交申请」**，以及逼你把方法写成可保护的形式——这本身会让论文更清楚。

### 5.4 可复制性（把「项目」变成「产品」）

现在 `rule` 表已经按 `scene` 分组，`FactProvider` 的雏形也在（`DiagnosisPipeline` 的事实组装）。继续抽两步：

1. 抽出 `FactProvider` 接口（`scene → List<Fact>`），变电场景实现放 `report` / `persona` 包，引擎不认识业务。
2. 抽「场景包」：一个场景 = 一组规则 + 一个事实模板 + 一个输出契约。换行业只换这三样。

**然后真的做一次迁移 Demo**：拿 6 条规则迁到「轨道交通检修」或「医院设备科」，跑通一次诊断。**有证据的「可复制」，和 PPT 上写「可推广」，是两个分数。**

工作量：5 人日（抽取 2 + demo 3）。

### 5.5 论文策略

已有 EI 初稿。建议改写成「**评测驱动迭代**」的版本：

- v1：18 条规则，召回 9.1%，发现 3 类缺陷
- v2：21 条规则，召回 85%+，误升档 0%
- 结论：规则增强不是「写规则」，而是「建可回放的评测闭环」

这个版本比「我们做了一个方法，效果不错」更有工程价值，也更难被质疑。红线不变：150 条 `output` 是 SFT 目标，只能叫 reference outputs，不能当模型成绩。

### 5.6 关于刚训好的 3B：能讲什么、不能讲什么（重要）

3B 训完是好事，但它会带来一个新的答辩风险：**eval_loss 0.0106 这个数字太漂亮，懂行的评委第一反应是「是不是训练集和测试集同源」。**

**能讲的（都是可核实的事实）**：

- 本地化：4-bit QLoRA，一张 8G 笔记本显卡（RTX 5060 Laptop）训完并服务，不依赖外部 API。
- 训练规模：300 步 / 5 epoch / 27427 秒，6 个 eval 点单调下降，无过拟合震荡。
- 工程指标：adapter 114MB；契约通过率 5/5（形状不合格重试 + 括号配平兜底后）；单次端到端约 95 秒；`source=model`、`unverified_numbers=null`、`fallback_note=null`。
- 结构指标：gaps 与技能雷达逐条一致、plan 的 `due_at` 严格递增、28 条事实引用。

**不能讲的**：

- 不能说「准确率 99%」。eval_loss 是 token 级交叉熵，不是业务正确率。
- 不能说「泛化好」。训练语料是脚本按同一份契约生成的，与评测同分布，属于 in-distribution 拟合。
- 不能把 `my_data15` 的 150 条 `output` 当模型输出（旧红线，依然有效）。

**要补的一件事（半天，性价比极高）**：

留出 30 条**从未参与训练**的真实脱敏档案做 holdout，只报三个数：契约通过率、事实引用正确率、缺口一致率。答辩时说「holdout 30 条，契约通过 28/30」——这比 eval_loss 0.0106 可信一百倍，也堵住了「数据泄漏」的追问。

**顺带一提**：3B 训成之后，`/api/v1/agent/{agentType}/{action}` 这个通用桩**仍然是写死的**（个人诊断走的是 `/personal/agent-diagnose` 另一条路）。两件事不要混为一谈——答辩时被问「你的 Agent 到底是模型还是规则」，答案必须是「同一个 DTO，`source` 字段告诉你这次走的是哪条路」，而不是含糊过去。

## 9. 一页纸答辩脚本（约 300 字，2 分半）

> 各位老师，先说一个反常识的判断：**行业 AI 的瓶颈不是模型不够强，是模型不可审计。**
>
> 变电运维有两件事不能妥协：安全不能出错，结论必须能追责。所以通用大模型在这里用不了——它写得很漂亮，但你不知道它为什么这么说。
>
> 我们的做法叫「双脑三账」。规则脑负责判断对错，模型脑负责说人话。每条建议背后有三本账：命中了哪条规则、依据了哪几个事实、谁采纳的、理由是什么。
>
> 这里有个数字：同一份 150 条档案，纯模型输出有 2.7% 的数字查不到出处、25.3% 的差距项和档案等级对不上；加了规则护栏之后，这两项都是 0，而且 450 次重复执行逐字节一致。
>
> 但规则不是万能的——我们的评测框架自己抓出 3 个规则缺陷，静默漏报 80%。修复后召回从 9.1% 提到 85%。**这说明我们有的不是一个 demo，是一套能自我纠错的闭环。**
>
> 现在，王总的真实问题是「明年新增两座站，我该招几个、转几个、外包多少」。请他拖一下这个滑块——30 秒，三套方案的三年总成本和风险都在这儿，每个数字都能点开看依据。
>
> 系统已上线运行，方法已投稿 ICAICE 2026，规则引擎和评测集可复现。谢谢。
