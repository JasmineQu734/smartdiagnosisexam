## 0 一页结论

| 维度 | 现状 | 一句话说明 |
|---|---|---|
| 数据存放 | 一套 MySQL 8（`train_system`），52 张表 | 主数据、业务数据、展示口径、Agent 结论、审计留痕全在一库；不依赖 Redis / 对象存储 / 消息队列 |

| 测试与 CI | 0 | `backend/src/test` 不存在，`.github` 下只有 IDE 的 java-upgrade 记录 |

## 2 数据放在哪里

### 2.1 数据库连接与建库方式

- 连接参数在 `backend/src/main/resources/application.yml`：默认 `jdbc:mysql://localhost:3306/train_system`、`root` / `123456`，可用 `SPRING_DATASOURCE_*` 覆盖。
- 容器里由 `docker-compose.yml` 把 `./db/init` 挂到 `/docker-entrypoint-initdb.d`，**只在 MySQL 数据卷为空时执行一次**；后续改表要人工补脚本（README 给了 `mysql < db\init\xxx.sql` 的手工命令）。
- 没有迁移工具（无 Flyway / Liquibase），也没有版本表。

## 3 数据怎么来：三条来源链路

按「数据是谁产生的」把 52 张表和 75 个接口拆开，只有三类来源。判断一个页面是不是真数据，就看它落在哪一类。

### 3.1 A 类：真实业务闭环写库（运行时产生，真数据）

| 业务 | 写入的表 / 字段 | 代码位置 | 关键事实 |
|---|---|---|---|
| 管理员统一开考 / 结束本场 | `exam.status`、`started_at`、`started_by`、`ended_at`；清空 `exam_round` | `ExamCenter.start()` / `close()` | 只有开考后员工端才出现「进入考试」 |
| 员工进入考试（发卷） | `exam_round`（`question_ids`、`session_id`、`started_at`、`total`） | `ExamCenter.enter()` | 按技能从 `question` 表取题，题库不足按实际题量发卷 |
| 交卷判分 | 更新 `exam_round`，插入 `exam_history` | `ExamCenter.submit()`（第 226 行写 `exam_history`） | 逐题作答明细只在响应里返回，**没有落库** |
| 练习抽题 / 交卷 | `practice_session`、`practice_stat`、`practice_history`、`memory_item` | `PracticeController.draw()` / `submit()` | 答错写错误记忆并降低该技能正确率 → 下次自动加题 |
| 实操报告填报 | `task_report`（含 `document_text`、`analysis` JSON、`severity`） | `ReportService.submit()` → `analyzeAndStore()` → `save()` | 提交即渲染正文并归因；`need_human_confirm=true`，但**没有确认接口** |
| 报告复算 | 覆盖写同一条 `task_report` | `ReportService.analyze()` | 切换 AI 配置后重算，历史结论不保留 |
| 组长导入资料 / SOP 填报 | `course_material`、`material_doc`、`material_item` | `MaterialImportService.uploadDocument()` / `submitSop()` | 真读 PDF / Word / XLSX / PPTX / TXT 正文（PDFBox + POI），规则出候选题，状态「待审核」 |
| 管理员资料审核入库 | `material_item.status` / `question_id` / `reviewed_by`，写入 `question` 或 `course` | `MaterialImportService.review()` / `storeItems()` | 审核通过前候选题不参与抽题 |
| 运行诊断 | `diagnosis_result`（scope = PERSONAL / EXEC） | `PersonaController.runDiagnosis()`、`CompanyController.runDiagnosis()` | 存「预置结论 + 本次编号 / 时间 / 份数」的快照 |
| 通用 Agent 建议 | `agent_suggestion` | `ApiController.agent()` | 内容是写死的 3 条建议（见 §3.3） |
| 管理员操作留痕 | `audit_log`（保留最近 300 条） | `AdminConsoleController.audit()`、`MaterialImportService.audit()` | 登录、上传、审批、开考、清痕等 |
| 实时记忆 | `memory_item`（每账号最多 8 条 `MEM-RT-*`） | `RuntimeMemoryStore.add()` / `trim()` | 诊断、练习、交卷都会写 |

### 4.2 每个 Agent 实际考虑的判定因素

#### （1）报告归因（A4）—— 全系统最完整的规则引擎

代码：`ReportAnalysisService.ruleAnalyze()`；规则数据：`gas_rule`、`analysis_keyword_rule`。

| 序号 | 因素 | 规则 | 说明 |
|---|---|---|---|
| 1 | 阈值方向 | `abnormal()`：`HIGH` → 数值 > 阈值；`LOW` → 数值 < 阈值 | 方向取自 `gas_rule.direction` |
| 2 | 余量比例 | `ratio = abs(数值 − 阈值) / 阈值` | 异常时：`ratio ≥ 20%` 判「高」、`≥ 5%` 判「中」、否则「低」；未超限但 `ratio ≤ 10%` 判「中」，并追加 `RULE-VALUE-NEAR` 提示上行风险 |
| 3 | 气体归因目录 | `gas_rule` 6 条（O2 / SF6 / SF6 微水 / H2S 等） | 每条带单位、阈值、报警方向、国家标准号、归因结论、3 条处置措施 |
| 4 | 现象关键词 | `analysis_keyword_rule` 7 类，**最多命中 3 条** | 泄漏类 / 分解产物类 / 过热类 / 局放类 / 受潮类 / 人员不适类 / 持续恶化类，每条对应一个归因 + 一条措施 |
| 5 | 严重度升级 | 命中「持续恶化」或「人员不适」→ 严重度逐级 +1 | 低 → 中 → 高 |
| 6 | 置信度 | `0.72 + 0.10（异常）+ 0.04 × 命中数`，上限 0.95 | 规则引擎不设满分 |
| 7 | 输出结构 | `conclusion` / `causes` / `actions` / `rule_refs` / `standard` / `confidence` / `input_excerpt`（≤600 字）/ `generated_at` | 结论一律 `need_human_confirm=true` |

开启大模型后走 AI 路径：`system` 提示明确「只依据给定文档与规则目录、不得编造文档中没有的数值」，`temperature=0.2`，强制 `json_object` 输出，连接与读取超时各 20 秒；调用失败自动回退规则引擎并附 `fallback_note`。

#### （2）个人学习诊断（A6）

结论在 `dataset_meta.personal.diagnosis.core` 里**预先写好**：

- `verdict.headline`：在岗技能不足为主，继电保护 L1→L3 是最大缺口，软压板逻辑是共同诱因。
- `verdict.reasons` 4 条：岗位要求 L3 / 当前 L1；理论考试 62 分低于合格线 80 分；110kV 定值核对超时 2 小时；师傅评价 78 分（动手强、软压板逻辑弱）+ 高压试验未独立开展。
- `gaps` 3 项：每项带 `severity`（HIGH / MEDIUM）、`priority`（P1–P3）、`impact`、`action`。
- `plan` 4 步：课程 → 带教 → 模拟考 → 补考，每步带目标技能、目标等级、`due_at` 与理由。
- `compound_path`：复合型人才路线 4 阶段 + 里程碑 + 收益测算（每年减少外委与加班约 ¥3.6 万）。

运行时只追加 `diagnosis_id`、`ran_at`、`source_label`、`evidence_count = 4 + 实时报告份数`。

#### （3）公司运行诊断（A7）

5 类输入：员工学习情况、证书与有效期、技能掌握与岗位要求差距、组长提交的实操检测报告、人工成本与外委支出。输出问题清单 + 措施清单（每条带 owner / cost_impact / expected）+ 成本测算 `current_total 1,006,000 → optimized_total 928,000 → saving 78,000`（口径：以在岗技能提升替代 2 名外委/月）。**除报告份数外都是写死的文案。**

#### （4）练习抽题（A5）—— 真实计算

```text
effort(技能) = 缺口权重 × max(0.2, 1.6 − 该技能历史正确率)
题量(技能)   = round(总题量 × effort(技能) / Σ effort)
```

- 缺口权重来自 `dataset_item.practice.gap-rules`：继电保护 3.0、高压试验 2.0、故障录波 2.0、倒闸操作 1.0、安全规程 1.0。
- 每个技能至少 1 题、不超过该技能题库可抽量；最后一档取剩余题量保证总数精确；正确率下限 0.2 保证高正确率技能仍有题。
- 同一技能内按「出题次数少 → 等级低」取题；传入 `skill` 时按专项练习绕过权重表。
- 答错写 `memory_item`（ERROR）并降低 `practice_stat` 正确率 → 下次该技能 effort 上升、题量增加，形成闭环。

#### （5）外网课程检索（A8）

打分口径：标题 6 分 → 检索词 4 分 → 标签 / 技能 3 分 → 平台栏目 2 分 → 匹配理由 1 分，最多返回 12 条。关键词为空时按技能缺口（`employee_skill.level < required_level`，缺口越大越靠前）排序；平台检索直达链接由 `external_course_source.search_url` 的 `{kw}` 占位替换得到。

#### （6）资料出题（A1 / A2）—— 规则解析

两条识别路径：① 文档本身是试题（题号 / 题干 / 选项 / 答案 / 解析）→ 按行块逐题提取；② 文档是规程条款（含「应 / 必须 / 不得 / 严禁 / 宜 / 需 / 确保 / 至少」）→ 生成判断题与单选题，干扰项取自同文档其他条款。上限 `MAX_QUESTIONS = 24`、SOP 路径 `MAX_SOP_QUESTIONS = 12`、知识章节 `MAX_CHAPTERS = 12`。实测 `new-exam-paper.pdf`（18 页、11878 字）识别出 24 道题，每条带 `source_ref`（如「第 8 页」）与 `confidence`，状态「待审核」。

#### （7）考试组卷（不是 Agent，但是抽题逻辑）

`drawPool(skill)` 过滤技能 → 按 `level + id` 排序 → 取前 `question_count` 道；题库不足按实际题量发卷并在清单里显示可抽题量。无随机、无难度分布、无题型配比（虽然 `admin.exam-config` 页面写了「单选 40% / 多选 30% / 判断 30%」）。

#### （8）`rule` 表的 6 条规则没有被使用

建库脚本写入了 6 条规则（技能等级缺口、考试低分、关键岗位备份不足、未来需求缺口、实操技能原因、未按 SOP 的人为 / 流程原因），但 **Java 代码里没有任何 `FROM rule` 查询**；规则逻辑全部硬编码在 Java 与 `dataset_meta` 里。文档第 9.2 章说的「规则执行结果写入 `rule_result` 表」也不存在（连 `rule_result` 表都没有建）。

## 7 结论

1. **数据层面是干净的**：一套 MySQL 承载全部业务与留痕，没有隐式外部依赖，数据来源可追溯到具体表与脚本；问题不在「数据放哪」，而在「结论是谁算的」。
2. **Agent 层面是「骨架 + 两处真实算力」**：报告归因与练习抽题是真算法，资料出题是真解析（规则），其余 5 处是静态结论或写死文案。文档把「计划」写成了「已实现」。
3. **上线前必须先解决 4 个 P0**：假认证、写死结论、无测试、文件不持久。这四项不解决，任何真实性验证（评测、审计、演示翻车）都会失败。
4. 建议推进顺序：P0-1 认证 → P0-2 去写死（先让接口诚实地返回「未实现」）→ P0-4 持久化 → P0-3 测试与冒烟 → P1 各项 → 再进入第二部分（第 16～20 章）的 Agent 训练与接入。

## 16 Agent 全清单与训练后接入方案

### 16.1 设计原则

1. **契约冻结**：Controller、DTO、接口路径保持不变，`source` 从 `rule` 改为 `model` 时前端不改一行代码；模型只替换 Service 实现。
2. **规则兜底**：模型超时、置信度低于阈值、输出结构不合法时自动回退现有规则引擎，并在响应里给 `fallback_note`（现有 `ReportAnalysisService` 已经是这个模式）。
3. **人工确认**：面向决策、面向员工发展、面向题库的结论一律 `need_human_confirm=true`，模型不直接写业务表；确认动作必须留痕。
4. **数据不出内网**：训练与推理默认内网；确需外部 API 时先做字段脱敏（姓名、工号、站所、设备编号、金额）。
5. **可追溯**：每次推理记录模型版本、提示词版本、输入摘要、输出、置信度、是否回退、耗时，作为复盘与再训练的数据源。

#### T1 题目结构化与归类 Agent（P0，替代 A1 / A2 的规则解析）

| 起步量 | T1：300～500 份文档 / 5000+ 题；T2：300 份报告（覆盖 6 种气体 × 高中低）；T3：200 条计划；T4：100 条决策 |
| 质量抽检 | 10% 双人标注，一致性 Kappa ≥ 0.7；每月复查一次标注漂移 |
| 版本绑定 | 数据版本 + 模型版本 + 提示词版本三件套绑定，每次推理都落 `agent_inference`，保证任一结论可复现 |
| 防泄漏 | 训练集里的人员姓名、工号、站所、设备编号出网前脱敏；训练产物只在内网流转 |
| 与业务解耦 | 训练数据从业务库导出到只读数据集，不直接在生产表上训练 |

### 16.6 演进路线与灰度顺序

| 阶段 | 时长 | 做什么 | 灰度方式 |
|---|---|---|---|
| 阶段 0 可信化 | 2 周 | §6 的 P0-1～P0-4 | 无（先把假的部分改成真查询或显式未实现） |
| 阶段 1 提示工程 + RAG | 2～4 周 | T1 先上（资料解析最容易验证）、T2 用 few-shot + 规则目录、T8 带教问答用 RAG | 按「资料导入」「报告归因」单点开关，规则兜底 |
| 阶段 2 数据回流 | 2 周 | 补齐 §17 的 1～5 项通道，开始积累人工标签 | 无模型变更 |
| 阶段 3 微调 | 6～8 周 | T1 / T2 / T3 用积累的标签做 LoRA 微调 | 按 `agent_type` 灰度：先 10% 员工，对比人工确认一致率 |
| 阶段 4 组织级 Agent | 6 周 | T4（计算与表述分离）、T5、T6 | 决策类先「只读建议」，确认后人工执行 |
| 阶段 5 助手类 | 持续 | T7、T9、T10 | 只读、不影响业务写入 |

### 16.7 评估指标汇总（建议写入验收标准）

| Agent | 离线指标 | 在线指标 | 门槛 |
|---|---|---|---|
| T1 题目结构化与归类 | 字段级 F1、技能 top1 / top3、重复题召回 | 管理员一次通过率、驳回原因分布 | F1 ≥ 0.90、top1 ≥ 85%、通过率 ≥ 70% |
| T2 报告归因 | 严重度一致率、causes top3 命中、编造数值率 | 班组长改判率、回退率 | ≥ 90% / ≥ 85% / = 0 / 回退 < 5% |
| T3 学习路径 | P1 一致率、证据可溯源率 | 计划步骤采纳率 | ≥ 85% / 100% / ≥ 70% |
| T4 人才决策 | 成本测算误差、数字可溯源率 | 措施采纳率 | ≤ 5% / 100% / ≥ 60% |
| T5 练习推荐 | NDCG、同技能正确率提升 | 练习到考试的成绩转化 | 正确率提升 ≥ 10% |
| T6 课程重排 | NDCG@12 | 点击 / 采纳率 | 提升 ≥ 20% |
| T7 SOP 出题 | 通过率、答案错误率 | 驳回原因分布 | 通过率 ≥ 70%、答案错 < 5% |
| T8 带教问答 | 忠实率、引用准确率 | 追问率、有用率 | 忠实 ≥ 90% |
| 通用 | 输出结构合法率 | P95 延迟、回退率、单次成本 | 合法率 ≥ 99%，P95 < 3s（内网小模型）/ < 8s（外部 API） |

### 16.8 部署形态与降级

| 项目 | 建议 |
|---|---|
| 首选形态 | 内网 GPU 推理 + 内网检索；模型选 7B～14B 指令版（14B int4 约需 10GB 显存，单卡 4090 / A10 可承载） |
| 检索实现 | 第一期不必引入独立向量库：`knowledge_point`、`material_doc.text_excerpt`、`standard_ref` 数据量小（几十到几千条），用 MySQL 全文索引 + 关键词召回即可；上万条以后再引入向量库 |
| 与现有代码对齐 | 复用 `Sql` 数据访问、`AI_ENABLED` 开关、`fallback_note` 回退说明、`agent_suggestion` / `diagnosis_result` 留痕表 |
| 密钥与配额 | 密钥走环境变量或密钥管理服务；每次调用记录 tokens、耗时、是否回退；按 agent_type 设日配额 |
| 降级顺序 | 内网模型 → 企业网关模型（脱敏）→ 规则引擎；任一环节异常都要保证业务可用，且对用户可见（`source_label` + `fallback_note`） |
| 合规 | 数据不出内网；模型输出仅作建议，决策类结论必须人工确认；对外展示标注「AI 建议」与置信度 |

## 18 其他可以提高完善的地方

### 18.1 安全与合规

- **身份**：接内网统一身份（或 Spring Security + JWT），服务端解析身份与角色，取消 `X-User` / `X-Role` 传身份的做法；`/reports/**`、`/agent/**` 也纳入鉴权。
- **最小权限**：当前只有 4 类角色 + 路径前缀；建议增加「数据范围」维度（本人 / 班组 / 部门 / 全公司），与角色解耦。
- **审计不可删**：`POST /admin/audit/clear` 允许管理员清空留痕（虽然保留 1 条删除记录），生产应改为归档 + 只读，或限制到超管并二次确认。
- **脱敏**：报告正文、现象描述里可能含人员姓名与设备编号；AI 调用、日志、导出都要走脱敏。
- **模型输出免责**：所有 AI 结论固定携带 `source`、`confidence`、`need_human_confirm`，前端显著标注「AI 建议，需人工确认」。
- **密钥管理**：`AI_API_KEY`、数据库密码走密钥管理服务，禁止出现在仓库与镜像层。

### 18.2 工程质量

- **测试金字塔**：先补纯函数级单测（`ReportTemplate.abnormal`、严重度分级、置信度、`MaterialAgent` 条款解析、抽题题量分配），再补接口级集成测试（提交报告 → 归因 → 文档渲染），最后补一条 Compose 冒烟。
- **契约测试**：`docs/api-catalog.md` 与 OpenAPI 做一致性校验，防止文档与实现再次分叉。
- **数据库迁移**：引入 Flyway，把 `001`～`007` 纳入版本；禁止在生产手工执行 SQL。
- **前端去掉静默兜底**：`getData` / `postData` 失败必须让页面显式报错；`App.vue` 的 demo 数据只在开发模式保留。
- **类型与校验**：后端请求体目前大量用 `Map<String, String>` / `Map<String, Object>` 接收，建议改为 DTO + `@Valid`，与 `ReportForm` 一致。

**本轮已做的代码清理（不含行为变更）**：

- 重复实现各收成一份：`support/Texts`（文本 / 数值 / 摘要口径）、`support/Users`（`X-User` 默认账号）、`material/MaterialCodes`（资料编号与 `sort_no`）、`support/DiagnosisPipeline`（个人与公司诊断的同一条管道）。
- 删除的分身：三处 `user(header)`、两处 `nextMaterialCode` / `skillCodeOf`、五处 `plain(BigDecimal)` 之类的数值转文本、两处 `excerpt`、`ExamCenter` 与 `MaterialImportService` 各自的私有 `row(...)`、`AdminConsoleController` 的 `blankToEmpty` 与 `text`。
- 删除的零调用代码：`DatasetStore.saveMeta / saveItem / deleteItem`、`RoleGuard.employeePage`、`ReportRecord.withAnalysis`、`RuntimeMemoryStore.size`、`PersonalStore.exists`、`RuleEngine.asList`。
- 顺带修掉一处输入外发：报告归因的大模型提示词原先送整篇正文，现已与留痕 `input_excerpt` 共用 600 字上限（`Texts.excerpt`）。
- 仍未动：`App.vue` 的 `demo*` 兜底常量与单文件体量、`ApiController` 里 3 个写死的 Agent 桩（按约定等模型训练后再接 `RuleEngine`）。

### 18.3 数据治理

- **口径字典**：为每个 `dataset_*` 键登记「含义、责任部门、更新频率、是否对外」；现在 21+ 个键只有内容没有说明。
- **指标血缘**：驾驶舱指标（完成率、缺口、成本）应能下钻到明细表与 SQL，避免长期依赖手填口径。
- **种子与生产隔离**：演示数据（张伟、李民、王总）与生产数据分开库或分环境，防止演示数据混入生产。
- **保留与归档**：`memory_item`（8 条）、`audit_log`（300 条）等硬编码上限改为可配置并按时间归档。
- **外网数据合规**：`005` / `006` 抓取的国标与课程数据只存标题、链接与校验状态，注明来源与抓取时间。

### 18.4 运维与性能

- **持久化**：上传原件与报告目录改持久卷；`file_object` 存相对路径并提供受权限控制的下载接口。
- **健康检查**：`/actuator/health` 检查数据库与磁盘；Compose 给 backend 加 healthcheck 与重启策略。
- **备份与演练**：MySQL 每日全备 + binlog，按季度做恢复演练，并把结果写进管理端「运行状态」而不是假数据。
- **可观测**：接口耗时、错误率、AI 调用次数与回退率、报告渲染耗时打点；关键链路带 `trace_id`。
- **性能**：报告 PDF 渲染（PDFBox）是 CPU 密集操作，加缓存与并发限制；`/personal/course-search` 目前每次全表扫描 `external_course`，数据量上来后加索引或缓存。
- **编号生成**：`COUNT(*)+1` / `MAX(id)+1` 改为数据库序列或 UUID，避免并发重复。

### 18.5 产品与体验

- **员工端闭环**：把「目标 → 学习路径 → 练习 → 考试 → 实操报告 → 证据回写 → 更新计划」做成一条可视化主线，现在这些信息分散在 6 个页面。
- **班组长端**：任务派发、批量评分、报告复核（T10）、SOP 出题（T7）应在一屏内完成。
- **老总端**：每个结论都要能下钻到「哪几个人、哪几份报告、哪几条记录」，现在只有结论文字。
- **管理员端**：资料审核加「批量通过 + 快捷改技能」，减轻单条审核负担。
- **移动端**：建议只做只读（看技能雷达、待办、报告），填报与审核仍在 PC。
