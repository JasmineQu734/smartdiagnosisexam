## 第 2 页｜一页看懂项目

**页面标题**

从能力数据到人才决策，训得起、用得准

**核心痛点**

- 培训成本高：老师傅停机带教、重复培训、培训与岗位缺口脱节。
- 能力看不清：技能等级、岗位要求和未来需求散落在系统与表格中。
- 异常归因靠人：同一份报告，不同人可能给出不同结论。
- AI 不敢用：外网大模型不可解释、断网不可用，结论无法复核。

**解决方案**

- 多源数据接入：考试、实操报告、培训记录和能力档案。
- 规则与算法引擎：按场景进行确定性匹配、计算和归因。
- 可解释结论输出：每条结论携带规则编号、事实依据和置信度。
- 人工确认闭环：建议、确认、执行和回滚全程留痕。

**结论**

一套平台，打通“能力画像 → 精准培训 → 异常归因 → 人才决策”全链路。

## 第 3 页｜项目背景与行业痛点

**页面标题**

变电运维最贵的两笔隐形成本

**痛点一：培训成本高**

- 老师傅停机带教，占用核心产能。
- 全员停线听课，打断生产节拍。
- 重复培训缺乏针对性，投入与能力缺口不匹配。
- 培训台账、证书和学时仍依赖人工维护。

**痛点二：用人决策盲区**

- 管理者难以判断是真实缺人，还是技能不足。
- 内部技能散落在档案、表格和个人经验中，人才难以被发现。
- 关键能力单点依赖，一人请假可能影响作业连续性。
- 用人建议缺少数据依据，结构性错配难以及时发现。

**量化证据（演示数据集 / 200 人厂测算口径）**

- 数据覆盖：2 家制造业演示企业、141 个账号，包含平台超管 1、企业管理员 2、部门负责人 8、班组长 5、员工 125。
- 传统成本基线：老师傅年均 200 小时停机带教；年 4 次全员停线培训；统一考核每人每次 30～40 分钟；约 40% 培训工时属于重复培训；单岗位课件编制 2～3 人天。
- 平台优化结果：单岗位课件压缩到 30 分钟内；CAT 测评由 25 题降至 8～12 题；示例排程覆盖 126 名员工、131 个培训时段，节省 158 停机工时；200 人厂每年 4 次考核约节省 93 停机工时。
- 关键岗位单点依赖：扫描发现 5 个技能断点，训练 3 人、投入 3.5 人天、成本 ¥1,980，消除 66 工时风险敞口；叉车工离职算例形成一条三跳替补链。
- 数据口径说明：以上为演示数据集与测算结果，不是企业真实试点数据；正式提交前应替换或补充真实调研、试点和用户反馈数据。

**底部结论**

把培训投入转化为可用的能力资产，让企业训得起、用得准。

## 第 5 页｜创新场景定义

**页面标题**

从“培训档案”走向“人岗能力持续治理”

**场景名称**

制造业产线人岗能力持续保障场景

**场景触发**

- 新岗位、新设备或新规程上线，需要快速生成培训内容。
- 考核、实操和日常培训持续产生新的能力数据。
- 岗位出缺、请假或临时顶岗，需要判断谁能够接替。
- 安全检查和监管核验需要快速调取培训与证书证据。

**场景创新**

- 让培训结果从“完成率”升级为“逐项能力掌握情况”。
- 让异常归因从“靠人讨论”升级为“规则命中 + 事实依据”。
- 让用人建议从“凭印象”升级为“可计算、可追溯、可申诉”。
- 让 AI 从“直接决策”降级为“只出建议、必须人工确认”。

**场景边界**

系统不输出裁员、降职、调岗、绩效排名和奖惩指令，只提供培训与用人分析建议。

## 第 6 页｜总体解决方案

**页面标题**

大模型做翻译，规则与算法做决策

**业务主链**

原始资料与业务数据 → 结构化能力事实 → 规则和算法计算 → 可解释结论 → 人工确认 → 决策留痕

**能力分工**

- 大模型：解析 SOP、生成课程和题目、把算法结果翻译成自然语言。
- 规则引擎：按场景和优先级完成确定性匹配，保证同一输入得到同一结论。
- 业务系统：提供人员、岗位、考试、实操和审计数据。
- 人工确认：采纳、驳回或修改，建议不会直接修改业务数据。

**两条底线**

- `source=rule` 现在，`source=model` 将来；替换模型不改变接口和前端。
- AI 只出建议，不直接改业务数据，所有结论必须可追溯。

## 第 7 页｜核心创新总览

**页面标题**

规则先行、模型后置的可审计智能闭环

**创新一：声明式规则入库**

- 条件与动作存于 MySQL JSON 字段，改规则不需要重新发版。
- 使用白名单算子，不执行 SpEL、脚本或动态 SQL。
- 支持优先级、启停、匹配分组、命中上限和事实引用。

**创新二：结论可解释到数据**

- 每条结论携带 `rule_code`、命中条件、依据事实和置信度。
- 规则结果、待确认建议和人工决定使用同一个 `run_id`。
- 支持复核、追责和二次计算，避免“模型说我不行”。

**创新三：离线可用与自动回退**

- 不依赖外网大模型，规则链路可独立跑通全流程。
- 外部模型未配置、超时、报错或输出不合规时自动回退。
- 回退原因写入 `fallback_note`，人工可查。

## 第 8 页｜算法引擎一：规则匹配与冲突消解

**页面标题**

规则引擎：确定性匹配、可复算输出

**输入**

- 场景：`PERSONAL_GAP`、`EXAM_RESULT`、`TALENT_GAP`、`REPORT_GAS` 等。
- 事实：考试分、技能等级、岗位要求、检测值、报告文本等。
- 规则：条件 JSON、动作 JSON、优先级、分组、启停和停匹配开关。

**算法流程**

1. 按场景读取启用中的规则。
2. 按 `priority` 从高到低排序，同优先级按 `rule_code` 稳定排序。
3. 对条件树进行白名单算子求值。
4. 按 `rule_group` 分别处理命中上限与停止匹配。
5. 合并 `actions`、`causes` 和 `rule_refs`，严重度取最高档。

**输出**

- `matched`：是否命中。
- `hits`：命中规则、条件和解释。
- `skipped`：无法判定的规则及原因。
- `verdict`：动作、原因、严重度、规则编号和置信度。

**实测数据（2026-09-26，本机规则自检）**

- 规则规模：共 18 条、启用 18 条，覆盖 5 个场景、3 个匹配分组。
- 重复一致性：同一输入连续执行 200 次，`rule_refs` 200 次完全一致，一致性 100%。
- 执行耗时：预热 20 次后采样 200 次，接口端到端平均 3.716 ms，P95 5.042 ms，最小 2.342 ms，最大 13.344 ms。
- 异常分支：11/11 个规则测试场景通过，覆盖率 100%；包含越权、优先级、`stop_on_match`、`max_hits`、无匹配、字段缺失和类型错误。
- 维护方式：规则变更只需更新数据库，无需修改代码、重新编译或发布；当前没有可比工时基线，因此不虚构“维护成本降低百分比”。

**配图建议**

用流程箭头展示“取规则 → 排序 → 求值 → 分组 → 合并 → 留痕”，右下角放一张事实结果截图。

## 第 9 页｜算法引擎二：气体检测双组匹配

**页面标题**

气体报告归因：余量档位与关键词分组匹配

**问题**

报告包含多种气体，每种气体又有超标、临界和正常等档位。如果为每种气体、每个档位分别编写规则，规则库将迅速膨胀且难以维护。

**算法设计**

- `VALUE` 组：根据检测值、阈值和余量比例确定严重度。
- `KEYWORD` 组：根据异常现象文本补充原因和处置措施。
- 两组独立匹配，避免一条规则命中后阻断另一组。
- `*_from` 引用事实，一条规则可服务所有气体与档位。

**真实案例**

- 报告：`RPT-20260919-0003`
- 气体：O2
- 检测值：18.2 %VOL
- 阈值：19.5 %VOL
- `VALUE` 命中：`REPORT_GAS_OVER_MARGIN_MID`
- `KEYWORD` 命中：`RULE-KW-HEALTH`
- 最终严重度：高

**三栏配图内容**

左栏：输入｜异常报告

- 报告编号：`RPT-20260919-0003`
- 检测地点：110kV 城北变电所电缆沟 A 段 #1 检查井
- 气体类型：氧气 O2
- 检测值 / 阈值：18.2 %VOL / 19.5 %VOL
- 异常现象：作业人员出现头晕、胸闷不适，已撤出并通风
- SOP 执行：未按 SOP 执行
- 截图要求：截真实报告填报页的“基础信息、检测数据、异常现象”三段

中栏：处理｜双组匹配

- 场景事实：`scene=REPORT_GAS`、`over_threshold=true`、`ratio=0.0667`
- `VALUE` 组命中：`REPORT_GAS_OVER_MARGIN_MID`，优先级 140
- `VALUE` 判定依据：`over_threshold(true) is_true`、`ratio(0.0667) gte 0.05`
- `KEYWORD` 组命中：`RULE-KW-HEALTH`，优先级 95
- `KEYWORD` 判定依据：报告正文包含“头晕、胸闷、不适”
- 命中规模：`VALUE` 组 1 条；`KEYWORD` 组 1 条
- 截图要求：不要截 SELECT 语句，截展开后的 `hits_json` 或查询结果

右栏：输出与确认

- 最终严重度：高
- 综合原因：受限空间通风不足或 SF6 聚集导致氧含量下降；人员出现身体不适
- 建议措施：停止作业、撤出人员、强制通风、复测合格后再进入
- 规则编号：`REPORT_GAS_OVER_MARGIN_MID`、`RULE-KW-HEALTH`
- 置信度 / 来源：0.8 / `rule`
- 执行编号：`R-20260922-152832-3B83`
- 确认要求：`need_human_confirm=true`
- 人工决定：`limin` 采纳 `ACCEPTED`，理由“结论与现场情况一致，按建议补充 SOP 卡并跟踪隐患”
- 截图要求：上半部截系统结论卡片，下半部截 `agent_suggestion` 或 `decision_log`

## 第 10 页｜算法引擎三：个性化组卷与题量分配

**页面标题**

按“技能缺口 × 历史正确率”动态组卷

**问题**

员工同时有多项能力缺口，固定套题会把有限的练习时间平均分给已掌握技能和高风险技能。系统需要把题量优先分配给缺口更大、当前答对率更低的技能。

**项目现状**

- 已实现入口：员工端 → 学习与考试 → 练习题。
- 已落库数据：`practice.gap-rules`（技能缺口权重）、`practice_stat`（个人逐技能正确率）、`question`（题目、等级、使用次数）、`practice_session` / `practice_history`（抽题与练习记录）。
- 抽题、交卷、正确率更新和错题写入记忆库已经形成闭环，不是预置结果。

**算法输入**

- 缺口权重：继电保护 3.0；高压试验 2.0；故障录波 2.0；倒闸操作 1.0；安全规程 1.0。
- 历史正确率：`正确题数 ÷ 已答题数`；没有练习记录时按 0.70 冷启动。
- 题库存量：按技能统计可抽题数，并从 `used_count` 少的题目开始选，避免反复抽同一题。

**算法公式与流程**

1. 计算每个技能的努力权重：`effort = 缺口权重 × max(0.2, 1.6 - 历史正确率)`。
2. 按 `effort` 降序排列，并按权重占比把本次题量分配到各技能。
3. 按顺序为技能分配题量；每个实际分配到的技能至少 1 题，但不能超过题库存量和本次剩余题量，题量耗尽后后续技能不再分配。
4. 技能内部按 `used_count` 升序、题目等级升序取题。
5. 交卷后更新 `practice_stat`；错题写入 `memory_item`，下次抽题自动提高对应技能权重。

**项目数据与复算示例**

- 初始题库：21 题，覆盖继电保护、倒闸操作、高压试验、故障录波、安全规程 5 项技能。
- 冷启动权重代入：继电保护 2.7；高压试验 1.8；故障录波 1.8；倒闸操作 0.9；安全规程 0.9。
- 一次抽 5 题时，当前代码复算分配为：继电保护 2 题、高压试验 1 题、故障录波 1 题、倒闸操作 1 题、安全规程 0 题。
- 口径说明：这是基于初始题库和无历史记录账号的规则复算示例，不是学习效果实验结论。

**配图建议**

左侧截“学习与考试 → 练习题”的 Agent 抽题策略与技能分配标签；右侧截交卷后的正确率与练习解析。底部用一条箭头写清“抽题 → 作答 → 正确率更新 → 错题入记忆 → 下次重新分配题量”。

## 第 11 页｜算法引擎四：课程内容匹配与缺口优先排序

**页面标题**

从“搜到课程”到“优先补当前缺口”

**问题**

外网课程数量多，关键词出现并不代表课程对当前员工有价值。系统需要同时判断课程内容与检索词匹配得有多准，以及课程技能是否对应该员工的岗位缺口。

**项目现状**

- 已实现入口：员工端 → 学习与考试 → 推荐资源 → 外网课程搜索。
- 已落库数据：`external_course`（课程标题、技能、标签、机构、匹配理由）、`external_course_source`（平台与检索入口）、`employee_skill`（当前等级、岗位要求）。
- 搜索结果、站内资源、平台实时检索入口在同一条业务链路返回，可截图、可点击验证。

**算法输入**

- 检索词：按空格、逗号、顿号拆分并去重。
- 课程字段：标题、平台检索词、标签、技能、机构、匹配理由。
- 个人缺口：`employee_skill.level < employee_skill.required_level`。

**打分规则**

- 标题命中：每个检索词加 6 分。
- 平台检索词命中：每个检索词加 4 分。

## 第 14 页｜标杆案例：气体检测异常归因

**页面标题**

同一份报告，同一套依据，同一个结论

**输入**

- 报告编号：`RPT-20260919-0003`
- 气体：O2，检测值 18.2 %VOL，阈值 19.5 %VOL。
- 现象：作业人员出现头晕、胸闷，不适后已撤出并通风。

**处理**

- `VALUE` 组命中：`REPORT_GAS_OVER_MARGIN_MID`。
- `KEYWORD` 组命中：`RULE-KW-HEALTH`。
- 严重度取最高档：高；置信度：0.8。

**输出**

- 原因：受限空间通风不足；人员出现身体不适。
- 措施：停止作业、撤离人员、强制通风、复测合格后再进入。
- 结论状态：需要班组长人工确认。

**结果**

- 同一条规则链可复算。
- 结论可追溯到规则编号、事实和人工决定。
- 人工确认后写入决策留痕。

## 第 21 页｜未来展望：三阶段演进

**页面标题**

从规则底座，走向更专业的行业训练 Agent

**总路线**

`规则全面落地 → 模型增强与数据回流 → 行业训练 Agent`

**阶段一｜规则底座全面落地（2～4 周）**

- 剩余场景全部接入规则引擎，支持规则新增、修改、停用和试算。
- 三个 Agent 桩接入规则 Service，保留命中依据、置信度和人工确认。
- 阶段结果：核心业务离线可运行，结论可复算、可追溯。

**阶段二｜模型增强与数据回流（6～8 周）**

- 不改接口和前端，增加 `source=model` Service，规则始终兜底。
- 用岗位、课程、考试、实操和历史决策构建知识库，人工确认结果沉淀为训练标签。
- 阶段结果：报告归因、资料校验和学习诊断升级为“规则 + 模型理解”。

**阶段三｜行业训练 Agent（3～6 个月，最终目标）**

- 融合岗位、技能、课程、考试、实操、带教和成本数据，形成企业训练知识底座。
- 用人工确认数据持续微调，让 Agent 能识别缺口、生成计划、推荐带教并安排复训。
- 最终形态不是聊天助手，而是越用越懂岗位、员工和训练闭环的行业训练 Agent。

**为什么它会越来越专业**

真正的壁垒不是通用大模型，而是企业长期积累的岗位标准、训练记录、实操报告、考试错题和人工确认结果。系统使用越久，训练 Agent 越了解这家企业“什么算达标、什么必须复核、怎样培养最有效”。

**结语**

先让规则保证可信，再让模型理解复杂场景，最后把企业自己的训练经验沉淀成行业训练 Agent。
